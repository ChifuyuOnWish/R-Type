    Audio¶

    Ownership and lifecycle¶

    Gui::open() attempts audio initialization unless GuiConfig::audioEnabled is false. An unavailable device leaves rendering and input operational. IGui::isAudioAvailable() reports whether this GUI owns a ready audio device.

    AudioSystem exclusively owns the device it opens. It refuses to take over an already initialized external device. Other code must not close its device. On shutdown, playback voices are stopped and unloaded before their shared source sounds; the audio device is closed last. Repeated shutdown calls are safe.

    Load effects¶

    Load effects after opening the GUI:

    if (gui.isAudioAvailable() &&
    !gui.audio().loadSound("shot", "audio/demo-shot.wav")) {
    std::cerr << gui.audio().getLastError() << '\n';
}

    Paths use the same asset root as visual resources, independent of the working directory. Sound IDs have their own namespace. Repeating an ID and normalized path reuses the sound; assigning that ID another path fails.

    Missing, empty, invalid or unsupported files and native buffer creation failures return false and populate getLastError(). Failed loads are not cached. The caller can report the problem and continue without that effect.

    Trigger effects¶

    const std::array<rtype::gui::SoundEvent, 1> events{{{"shot"}}};
gui.playAudio(events);

    The client supplies events when they occur. The GUI does not infer gameplay events from rendering data. Unknown sound IDs are skipped and recorded in the audio manager's last error. Playback is a no-op when audio is unavailable.

    Each loaded effect has eight playback voices sharing its sample data. Repeated events can overlap, including multiple instances of the same effect. If all eight voices for an effect are playing, a new instance is dropped. Existing voices and other effects continue; no voice is stolen.

    Volume and mute¶

    Players can adjust and save these values through Settings. The GUI defaults to 50% volume, unmuted.

    gui.setAudioSettings({0.5F, false}); // Half volume
gui.setAudioSettings({0.5F, true});  // Mute

    Settings can be applied before opening the GUI or during playback. Volume must be finite and between 0 and 1; invalid settings throw without changing the previous settings. Updates affect existing and future voices.

    Muting sets existing voices to zero volume while their playback continues. New events are discarded while muted. Unmuting restores the configured volume. Saved preferences are loaded on opening. Explicit API audio settings override the saved audio values; use Apply and save to persist session changes.

    Current client integration¶

    After opening the GUI, the client loads the two existing generated test effects: audio/demo-shot.wav as shot and audio/demo-hit.wav as hit. These are placeholder tones, not a final sound pack. No new audio assets are required.

    The client decodes GameEvent messages from the server and maps them as follows:

    Server event Sound ID
    Shoot shot
    Hit hit
    Kill hit
    PlayerDeath hit

    Sounds are triggered by received server events, including other players and enemies, rather than local keyboard presses. The client does not display event notices. Muting or disabling audio currently has no equivalent event text.

    Events received while Settings or a connection status page is displayed are not played or queued for later. Network and world updates continue. Voices already playing may finish. Volume, mute and overlapping voices follow the AudioSystem rules above. Missing sound assets are logged and skipped without blocking gameplay or rendering.

    Verification¶

    Run a server and a connected client with an audio device available. Hold Fire and check that server-confirmed shots produce sound. Change volume, mute and unmute in Settings; apply each change. Check that mute and --no-audio suppress sound without affecting gameplay. Missing assets must not prevent movement or rendering.

    The automated audio test replaces native audio calls with a fake backend to check initialization failures, loading, overlapping voices, volume, mute and cleanup ordering without a physical device. These checks do not confirm the new server-event playback on real hardware; that requires a manual check.
